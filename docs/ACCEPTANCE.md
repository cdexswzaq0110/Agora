# 用 Agora 開始工作驗收

這份清單給「開始用 Agora 做真正的開發工作」時照著走。每一步都寫了要看什麼證據、什麼情況要停下來回報。

## 0. 準備（一次）

1. 安裝最新版（GitHub Releases 的安裝檔，或自己 `cargo tauri build`）。打開後頁尾版本應是 v0.6 以上。
2. **設定 → 模型**：Claude 與 Codex 都顯示「就緒」；選好預設模型與推理強度。
3. **設定 → 審查者唯讀證明**：對 Claude 與 Codex 各按一次「證明唯讀」（各花一次很小的呼叫）。兩個都要顯示「已證明」——沒證明的提供者，審查結論最高只到「推論」。
4. **Skills 頁**（命令面板 Ctrl K →「Skills」）：bundle 版本 2.0.0、9 個核心 skill 都是「已驗證」。有「已停用」就停下來回報。
5. 手機（選用）：頁尾「手機連線」照步驟配對。

## 1. 選一個真的程式庫

- 首頁（團隊）的「程式庫」選單 → 新增程式庫，選一個**有 git 的**資料夾（沒有 git 時版本無法確認，結論最高只到「推論」）。
- 第一次建議用一個小、可回復的改動來驗收整條流程。

## 2. 團隊工作流：從構想到任務

在首頁寫構想、選類型與深度 →「建立工作流」，然後一階段一階段核准：

| 階段 | 你要看的 | 停下來回報的情況 |
|---|---|---|
| 構想收斂 | 「待你回答的問題」——回答後再核准 | 問題與你的構想無關 |
| 可行性分析 | 「建議：做／調整後再做／不做」與理由；要不做就選「只保留不實作」 | 結論與理由矛盾 |
| 需求與體驗 | 每個使用者故事都有**可檢查**的驗收條件 | 驗收條件無法判定（例如「好用」） |
| 技術設計 | 架構、API、資料模型、ADR；「保留的異議」「需要你決定的事」 | 有重大異議卻沒有列出選項 |
| 任務拆分 | 每個任務有驗收條件與驗證指令 | 任務太大（一個任務改很多模組） |

每個階段頁面上都看得到：每則發言用了哪個 skill（標籤）、團隊名冊裡每個角色的紀錄（完整／簡查／不適用／**缺漏**）。缺漏很多時回報。

## 3. 把一個任務交給工作坊

任務清單 →「交給工作坊」→ 等方案整合好：

1. **核准前**看方案的「驗收標準」：每一條都要能被別人或程式判定。核准後專案頁會出現「驗收合約」（AC1、AC2…）。合約條數與你看到的不一致 → 回報。
2. 填**驗證指令**（例如 `cargo test`、`npm test`）——沒有它，結論不可能是「已確認」。
3. 實作完成後看專案頁的審查面板：
   - **規格審查**：每一條的判定與證據（檔案位置或驗證輸出）。
   - **品質審查**：發現的問題與嚴重度。
   - **審查紀錄**：每次審查有沒有被採用、為什麼不採用、版本是否一致。
4. 結論：

| 結論 | 意思 | 你要做的 |
|---|---|---|
| 審查通過・已確認 | 驗證指令通過、版本一致、審查者唯讀已證明、每條都有證據 | 看 diff → 套用到程式庫 → 自己 commit |
| 審查通過・推論 | 少了上面某一項（看注記） | 補上缺的那一項，或自己確認後再套用 |
| 有條件無法確認 | 審查者無法判定某幾條 | 看原因，自己判斷或補驗證方式 |
| 審查回覆無法採用 | 兩次回覆都格式錯誤或版本變動 | **回報**（附匯出的 Markdown） |
| 已達修訂上限 | 改了幾輪仍有條件沒過 | 看未過的條件；必要時縮小任務重來 |

## 4. 回報方式

專案頁「匯出 Markdown」，附上：程式庫、你預期什麼、實際看到什麼、審查紀錄裡的原因。只花模擬模型的「示範模式」不能當驗收證據。

## 5. 一律停下來回報的情況

- Skills 頁有「已停用」的 skill。
- 同一個專案反覆出現「審查期間工作區有變動」（可能有別的程式在改那個資料夾）。
- 「審查者的唯讀還沒有被證明」，但你已經按過證明。
- 額度保護或呼叫上限擋下了你認為不該擋的工作。
- 任何「已確認」的結論，事後發現其實沒做到。
