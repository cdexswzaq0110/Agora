# 0012 — 合併重繪時，「只重畫一則」吃掉了「整頁重畫」

- **Date**: 2026-11-16
- **Grade**: 已確認（重現 2/2 次失敗 → 修正後 3/3 次成功）

## 發生了什麼

v0.4 驗收段落留言時，模擬工作坊從「整合」進入「等待核准」，伺服器與 `S.rec` 都已經是 `awaiting_approval`，畫面卻還停在「整合」：頁首狀態是舊的，核准面板是空的。重新整理後就正常了。

議題頁有兩種重繪請求，共用同一個 `paintQueued` 布林值：

- `scheduleTurn(i)`：串流文字到達時，只重畫第 i 則發言；
- `schedulePaint()`：`plan`、`phase`、`status` 等結構性事件到達時，整頁重畫。

順序是：最後一段文字（`delta`）先排了一個「只重畫一則」的畫格，接著 `turn_ended`、`plan`、`phase`、`status` 在**同一個畫格之前**陸續到達。`schedulePaint()` 看到 `paintQueued === true` 就直接 `return`，那個畫格執行的卻是「只重畫一則」。直到下一個事件才會整頁重畫，而進入核准關卡之後，正好不會再有事件。

## 證據

- 修正前：開兩個模擬工作坊，進入等待核准後 1.5 秒，`#sGate` 的長度是 0、狀態欄是「整合」；`S.evlog` 的最後幾個事件是 `delta, delta, quota, turn_ended, plan, phase:等待核准, status:awaiting_approval`。手動送一個 `note` 事件，就會立刻畫出核准面板。
- 修正後：連續 3 次，進入等待核准後 400 ms 內核准面板都已出現（8 個段落留言按鈕都在）。

## 和 lessons/0005 的關係

[0005](0005-raf-does-not-fire-in-hidden-pages.md) 記錄的症狀完全一樣（「畫面停在『修訂方案』，沒有核准面板；重做一次又正常」）。當時推測是「頁面在背景，rAF 不觸發」，標為「候選」。那個推測不一定錯，`nextFrame()` 的計時器備援也仍然需要；但這次的重現證實了另一個原因，而且這個原因不需要頁面在背景。

## 規則

- 合併多個請求時，強的請求要能**升級**已排程的那一次，不能因為「已經排程了」就被丟掉：`session.js` 改成 `frameQueued` ＋ `fullPending`，畫格執行時，有 `fullPending` 就整頁重畫。
- 即時畫面的驗收要包含「**事件流中途**進入某個狀態」，不能只測「載入時就已經在這個狀態」。v0.3 驗收核准面板時用的都是已經在等待核准的議題，所以沒抓到這個問題。
