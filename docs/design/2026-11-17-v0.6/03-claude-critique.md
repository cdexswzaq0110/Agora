# v0.6 · Claude 對 GPT 提案的互評

> 第二輪。寫完之前沒有看 GPT 對 Claude 提案的互評。使用者在第一輪後決定：議題 → **專案**，原本的專案（工作資料夾）→ **程式庫**。

## GPT 比我好的地方（採用）

1. **skill 收據由程式產生**：每次呼叫記錄 `skill_id@version` 與注入內容的 SHA-256，並量四個比例（應注入／已注入／模型回報／輸出契約通過）。比我只記 skill 名稱更可稽核。採用；但「模型回報的 SKILL_RECEIPT」只當參考，見下方。
2. **把近義入口合併**：discovery／clarify／design 讓模型先猜路由；合併成一個「問題定義」，用參數決定輸出。採用（在 Agora 裡由程式選，影響較小；但使用者直接開 CLI 時影響很大）。
3. **規格審查與品質審查是兩個 skill**，而且品質審查只在規格全部通過後才做。比我「一次呼叫兩段」清楚；成本問題用「小型低風險任務可同一 session 分兩段」解決。採用。
4. **測試由 Agora 在 agent 沙盒外執行**（Windows 上 `spawn EPERM` 的實測）。Agora 本來就是這樣做；寫進驗收標準。
5. **刪掉「每輪強制寫 lesson」**：帳本與規則單向增長的根源之一。改成「有會再用到的領悟才寫」。採用。
6. **skill 驗收要有正例、反例、對抗例與開／關對照**，沒有量得到的改善就降為選用。採用；但真實 CLI 的大量評估移到之後的階段（成本）。
7. 團隊五階段只做**文件契約完整性審查**，不套程式品質審查。採用。

## 我認為 GPT 有問題的地方

| # | 問題 | 建議 |
|---|---|---|
| 1 | **「Agora 只用 prompt 宣告唯讀」不正確**：`provider/claude.rs:95` 唯讀時傳 `--permission-mode dontAsk --allowedTools Read,Grep,Glob,WebSearch,WebFetch`，`provider/codex.rs:187` 傳 `-s read-only`。缺的是**證明旗標有效的探測**，不是旗標本身 | 探測放第二階段；第一階段把現有旗標寫進文件與測試 |
| 2 | **canonical 來源放在 Agora**，會讓使用者的 harness（SE）變成下游產物；但使用者要的是「改進這兩個 harness」並在一般開發中使用，SE 也要能不靠 Agora 單獨用。SE 的消融與領悟帳本（規則演進的證據）也在 SE | **來源放 SE repo**（`skills/` 標準格式＋manifest）；Agora 與 SE-Codex 各放一份**固定版本**的副本（版本號＋hash），由同步腳本更新，CI 檢查副本與來源一致 |
| 3 | 名稱用 `agora-*` 把 skill 綁在 Agora | 用 **`se-*`**（使用者 harness 的品牌），在 Agora 之外也能用 |
| 4 | 「工作區」命名 | 使用者已決定「程式庫」；而且「工作區」已經是隔離 worktree 的名稱 |
| 5 | **git 指紋放到第二階段**：但它很便宜（Agora 的 worktree 已經在呼叫 git），而且是「審查看的就是測試的那一版」的唯一保證 | 第一階段做簡化版：驗證前、審查後各取一次（HEAD＋`git diff HEAD` 雜湊＋未追蹤檔清單），不同就記錄並把結論上限降為推論 |
| 6 | **第一階段沒有改兩個 harness 本身**（使用者最主要的要求），四個階段都在 Agora | 第一階段必須包含：SE 精簡入口、skill 換成標準格式、hooks 失敗即擋且跨平台；SE-Codex 模型改讀能力清單、預設單次＋外部驗證、skill 改從 SE 同步 |
| 7 | 模型回報的 `SKILL_RECEIPT` 可以造假，提案自己也說真正證據由程式判定 | 不要求模型回報；收據只由程式產生（注入的 hash＋輸出契約檢查結果） |
| 8 | 每個 skill 5＋5＋3 個案例 × 9 個 skill，若全用真的 CLI 跑，第一階段成本很高 | 第一階段：案例寫好，用模擬模型與輸出契約檢查跑；真的 CLI 開／關對照放第四階段，附預算 |
| 9 | 整份標「已確認」：架構建議是推論 | 依規則分開標 |

## 兩份都漏掉的

- **團隊階段已經有一套方法論寫在程式裡**：`team.rs` 的 `stage_goal`、`stage_required`、角色的 `duty`。導入 skill 後要變成**單一來源**（階段方法由 skill 提供、程式只保留結構檢查），否則同一件事兩處定義、會漂移。
- **18 個角色卡要合一**：`team.rs` 的 `ROLES.duty` 與 SE 的 `ROLE_MODEL.md` 各寫一份。
- **提示詞預算**：團隊階段已經放了構想（≤8,000）＋上游文件（≤6,000×4），議題上限 40,000 字；skill 本文要有上限（例如每個 ≤4,000 字、每次最多兩個），超過時截斷要標示。
- **Codex 會自己讀專案的 `AGENTS.md` 與 `.agents/skills`**：專案安裝了 harness 後，Agora 再內嵌一次會重複。第一階段一律內嵌（不安裝到專案），安裝放第三階段並處理去重。
- **使用者要開始「用 Agora 驗收」**：需要一份驗收清單（怎麼開一個真的專案、看哪些證據、哪些情況要停下來回報），以及在 Agora 裡就看得到每個 turn 用了哪個 skill。
- **兩個 harness repo 的交付方式**：SE 的歷史是 PR 合併；改動應該開分支、PR，而不是直接推 main。

## 建議的最終範圍

**第一階段（這一輪）**
1. SE：skill 改為標準格式、9 個核心 skill（合併近義入口、拆開兩種審查）、入口 ≤100 行、移除強制 lesson、hooks 失敗即擋＋自我測試、同步腳本、manifest（版本＋hash）。
2. SE-Codex：skill 改從 SE 同步、模型讀能力清單、預設單次＋外部驗證、文件更新。
3. Agora：harness 副本＋登錄表、階段／角色 → skill 確定性注入（有上限）、程式產生的 skill 收據、團隊階段方法改由 skill 提供（單一來源）。
4. Agora：AC 合約封存、規格審查逐條 JSON 驗證、品質審查在規格通過後、git 指紋簡化版、結論上限規則。
5. Agora：議題 → 專案、專案 → 程式庫；Skills 頁（看每個 skill 的版本、用在哪、被用幾次、契約通過率）。
6. 驗收清單文件。

**延後**：審查者唯讀探測（第二）、安裝 harness 到專案（第三）、真的 CLI 開／關評估與精簡（第四）。

整體證據等級：推論（repo 現況的引用為已確認）。
