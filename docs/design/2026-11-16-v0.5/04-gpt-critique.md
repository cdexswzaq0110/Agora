## 互評結論

Claude 的方案更像「可直接映射到現有工作坊的階段編排器」；我的方案則在狀態模型、相依失效、成本控制與可測試性上更完整。最佳整合方向不是新增新引擎，而是以 `ProjectWorkflow` 編排多個既有 `Workshop` session。

## 1. Claude 比我好的地方

- **核心範圍抓得更準。** Claude 明確把 0–3 定為本輪核心、4–6 先產文件；我的八階段 MVP 把實作、上線也納入，範圍偏大。
- **「下一步」導向更清楚。** 「待你回答／待你核准／可開始下一階段」比我的三欄介面更貼近使用者作為團隊負責人的操作心智。
- **全員出場規則更直接。** 每個相關階段都要留下角色段落，不適用也須說明，比我只要求一筆 `RoleCheck` 更能避免角色名冊淪為裝飾。
- **文件匯出位置具體。** 指定 `docs/agora/`，比我只寫 Markdown／ADR 匯出更可執行。
- **階段文件就是核准後方案文字**，概念簡單，能直接重用現有 synthesis 與 approval loop；我的通用 `Artifact` 模型較完整，但第一版成本更高。

## 2. Claude 的錯誤、風險與修正

1. **不應新增 `Mode::Stage`。**  
   現有 `Mode` 是執行演算法；`runner.rs`、`modes.rs`、驗證與呼叫估算都有 exhaustive match。加入 Stage 會迫使多處修改，卻沒有新對話演算法。  
   **修正：** `ProjectWorkflow → StageRecord → session_id`，每階段仍建立 `Mode::Workshop`、`Roundtable` 或 `Solo` session。

2. **把 `stage`、`roles`、`context` 塞入 `SessionSpec` 會混淆責任。**  
   現有 `SessionSpec` 已負責模型參與者、核准、worktree、驗證與 seed；職能角色不是現有 `Role` 流程角色。  
   **修正：** 職能角色放在 `RoleCheck/RoleAssignment`；送出 prompt 時轉成角色章節，不改 `Role` enum。

3. **完整深度「約 40+」低估。**  
   若 18/19 個角色在多個相關階段各自呼叫，0–3 很容易超過 50–70 次。  
   **修正：** 完整模式也按職能小組呼叫，只有明確要求才允許單角色獨立呼叫；UI 顯示由實際執行計畫計算出的精確值。

4. **標準模式 16 次仍偏貴，而且每階段固定紅隊過度設計。**  
   構想收斂與一般 PRD 不必都做雙提案＋整合＋紅隊。  
   **修正：** 紅隊預設只用於可行性與技術設計；其他階段採單次產出＋另一模型審查。

5. **新增安全工程師合理，但不該成為 v0.5 必做的第十九個角色。**  
   使用者明確要求的驗收基準是原列角色；擴充角色會增加 UI、提示詞及測試面積。  
   **修正：** 安全先作為 Architect／QA 的固定檢查面，後續再升格為可設定角色。

6. **缺少文件修訂的失效傳播。**  
   前階段重新核准後，下游文件可能已過期。  
   **修正：** 記錄 artifact revision 與 dependency revision；上游變更時將下游標為 `stale`，不可直接沿用舊核准。

## 3. 兩份都漏掉的事

- 階段執行的 idempotency、重試、取消及重啟恢復；重複點擊不能建立兩組 session。
- 既有專案不是綠地專案：需要「讀取現況」入口，避免假設從構想開始。
- 結構化產出契約；只靠 Markdown 小標題不容易可靠驗證角色是否真的完成責任。
- 角色意見衝突的處理規則：保留異議、由誰裁決、哪些決策必須升級給使用者。
- 桌寵助理需要穩定的提醒契約，例如 `next_action_changed`／`approval_required`，包含專案、階段、摘要、深連結與是否阻塞；桌寵實作本身仍不在本次範圍。
- 敏感內容與上下文裁切規則：哪些檔案可送入 CLI、摘要如何保留來源與證據等級。

## 5. 建議整合版

**v0.5 最終範圍：** 0 構想收斂、1 可行性、2 需求與 UX、3 技術設計、4 可執行任務；任務只能建立既有工作坊，不在此功能內自動部署。十八角色都有 `完整／簡查／不適用` 紀錄；安全作固定檢查面。

**階段劃分：**

1. MVP-A：workflow、stage、revision、dependency、role check、核准狀態。
2. MVP-B：以既有 session 編排各階段、重啟恢復、精確呼叫預估。
3. MVP-C：階段軌、文件、團隊、待核准與下一步。
4. MVP-D：工作坊 handoff、`next_action_changed` 事件、測試與 Manual GC。

**標準深度預設 9 次規劃呼叫：** 構想 1、可行性 2、需求 UX 2、技術設計 3、任務拆分 1；實作後交叉審查另加 1 次。快速模式 5 次，完整模式依執行計畫精算，不承諾固定上限。

**實作順序：** 狀態與 store round-trip → 編排器及 MockProvider 呼叫數 → 核准／stale／重試 → API 與 SSE → UI → 工作坊 handoff → `cargo test --workspace` 與 `node scripts/check-web.mjs`。
