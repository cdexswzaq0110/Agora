## 互評結論

### 1. Claude 提案比我好的地方

Claude 的最大優勢是「實測證據更完整」。它提供頁高、首屏位置、欄位數量、手機頂欄高度及 CLI 實測版本，讓優先級有客觀依據；我的提案雖指出相同問題，但量測細節較少。

幾個設計也比我更務實：

- 情報加入 `first_seen`、`streak`、關注主題命中變化，比我只設計 `new/continuing/rising` 更能回答「今天和昨天差在哪」。
- 逐段留言只放在 `h2/h3`，比我為每個 paragraph/list 建立 `block_id` 簡單很多，也更符合 MVP；我的方案在這點過度設計。
- 手機鍵盤出現時利用 `visualViewport` 隱藏底部導覽，並明確處理插話列與底部面板，考慮得比我完整。
- 快捷鍵開關對應 WCAG 2.1.4，且清楚區分裝置偏好應放 localStorage，這是我的提案漏掉的。
- 驗收標準涵蓋 375px、焦點還原、舊格式相容及 console error，整體比我的 UI 驗收更完整。

### 2. 錯誤、風險與修正建議

**情報趨勢定義不夠嚴謹。**「最近 7 天中的第一次」不能稱為真正的 `first_seen`，只能叫 `first_seen_in_window`。`streak` 也必須定義缺少某日情報、來源抓取失敗及同日重新產生時如何處理。建議抽成純函式，只比較嚴格早於今日的 digest；URL 優先，無 URL 時才用「來源＋正規化標題」。`rising` 不應混用 score 與 `stars_today`，只能比較相同來源、相同欄位，並記錄 `previous_metric` 與 delta。這方面我的提案較保守、正確。

**已讀日期集合無法處理同日更新。** 同一天重新產生情報後，日期仍在已讀集合中，新內容不會亮點。應像我的方案記錄 `generated_at`，已讀游標至少包含日期與產生時間；成功載入後才標記，寫入沿用既有 atomic store。

**effort 使用任意 `String` 風險高。** UI 下拉不能取代後端驗證。建議使用封閉 enum，provider/model capability 由後端回傳；不支援值回 400。Codex 可讀 `model/list`，但應有靜態保守 fallback，不能讓 app-server 探測失敗阻斷設定頁。Claude CLI 舊版本不支援 `--effort` 時應回可操作錯誤，不能靜默重試。

**記憶用「記憶：」文字解析過脆弱。** 模型可能漏標籤、輸出多行或把提示內容當記憶。至少需限制單行與長度、移除換行、拒絕空值，並在寫入前顯示實際預覽；`POST /remember` 無 body 時保留舊行為。

**快捷鍵範圍過大。** `/` 搜尋目前沒有明確的全域搜尋元件，`n`、`[`、`]`、`e` 又增加狀態與衝突測試。v0.4 先做 `?`、頁面跳轉及一個非單鍵命令入口即可，其餘延後。

`outline: none` 雖作用於非互動 h1，但完全取消提示不是最佳選擇；建議保留不改變版面的底線或 offset 樣式，同時確認按鈕等互動元件焦點環仍存在。

### 3. 兩份都漏掉的事

- 趨勢計算的日期時區、缺日、來源部分失敗及同日重跑語意。
- 已讀狀態與 digest 寫入同時發生時的競態測試。
- effort 實際記錄到 `Turn`，否則事後無法稽核某輪用了哪個強度。
- API 文件、技術文件及舊 JSON fixture 的同步更新。
- 設定 dirty bar 遇到儲存失敗、瀏覽器重新整理及返回鍵時的行為。
