# 07 · 記憶與上下文

原始碼：`compact.rs`、`memory.rs`、`repo.rs`、`prompts.rs::build`。

每則發言的提示詞，依序由這些部分組成：

```
角色與規則（家族、角色、模式、輪數、讀寫權限、證據等級的寫法）
## 專案記憶       ← memory.rs（短的原文帶入，長的依議題檢索）
## 專案快照       ← repo.rs（只給提案、評論、總結、與談、正反方、裁判）
## 議題
## 核准的方案     ← 只給工作坊的執行者與審查者
## 目前為止的發言 ← compact.rs（超過預算就記憶壓縮）
## 使用者插話
## 你這一輪的任務
```

## 記憶壓縮（`compact.rs`）

- 預算：`transcript_budget_chars`，預設 24,000 字。
- 最近的 `max(參與者數, 2)` 則發言保留原文；太長的話保留開頭和結尾，中間標「…中略 N 字…」。
- 較早的發言做**擷取式摘要**，依優先順序保留：
  1. 標題，以及含有「結論、建議、共識、分歧、風險、VERDICT、勝方……」的行。
  2. 條列項目。
  3. 第一行。
- 每段摘要後面都標註「記憶壓縮：原文 X 字 → 摘要 Y 字；全文保留在議題紀錄」。
- 連摘要都放不下時，省略最早的幾則，並寫明「省略最早的 N 則」。
- 這則發言會標記 `context_compacted`，過程紀錄也會記一筆，說明壓縮了哪些發言、字數從多少變成多少。

為什麼用擷取式而不是叫模型摘要：不花額度、結果確定，而且不會在摘要時加入模型自己的詮釋。

## 檢索式專案記憶（`memory.rs`）

專案記憶是累積下來的「決策與教訓」，例如在議題頁按「存入專案記憶」時，會加上一行「- [日期] 標題（模式）：結論【等級】」。

- 不超過 3,000 字時，整段原文帶入。
- 超過時：
  1. 切成條目：以 `- `、`* `、`#` 開頭的行開始一個新條目，其他行接在前一個條目後面。
  2. 最近 5 條一定保留。
  3. 其餘條目依和議題的 **TF-IDF 相關度**排序，在預算內盡量放；分詞方式是英數單字加上中文**相鄰兩字**。
  4. 依原本的順序輸出，開頭寫明「從 N 則中選出 M 則」。

測試：`selects_relevant_and_recent_entries_within_budget`：40 條無關的條目當中，一條講 PostgreSQL 的舊決策，會因為議題問到資料庫而被選進來。

## 專案快照（`repo.rs`）

在工作坊、討論、辯論開始時產生一次（`context_pack`，預設開啟），內容包括：

- 檔案樹（深度 2、最多 120 項，略過 `.git`、`node_modules`、`target`、`dist`……）
- README 的前 1,500 字
- `git log --oneline -8`
- 未 commit 的變更數量

總長度上限 6,000 字。用意是讓「第一份提案」就有根據；模型仍然可以自己讀任何檔案。

## 分岔（延續之前的討論）

議題頁每則發言旁邊都有「分岔 ↗」按鈕：把那則以前的發言複製成新議題的開頭（`seed`），你可以換個模式、改寫議題，從那裡接著進行。被複製的發言會淡化顯示，不算在新議題的發言數與 tokens 裡。
