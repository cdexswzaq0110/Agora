# ADR-0003: 方案工作坊與核准關卡

- **Status**: accepted
- **Date**: 2026-11-16
- **Evidence grade of the problem statement**: 已確認（使用者原話：「我的核心是希望協作討論後給出更好的方案，再去實作」）

## Context

v0.1 的「協做」模式是執行者先做、審查者再挑錯，但**方案本身沒有被討論過**：執行者拿到題目就直接動手，兩個模型的觀點只在事後的審查裡交會。v0.1 的「討論」和「辯論」可以產出好的方案，卻不會接著實作。使用者要的是兩件事串起來：**先討論出更好的方案，再實作**。

## Options considered

1. **在「討論」後面接「協做」**：讓使用者手動開兩個議題。中間的銜接靠人複製貼上，容易掉資訊。
2. **一個模式從頭跑到尾，不停下來**：最快，但「更好的方案」由誰判定？模型自評的方案未必是使用者要的；而且實作是最花額度的階段（實測一次約占 5 小時窗的 8%），應該在花之前讓人看一眼。
3. **一個模式，中間有核准關卡（選這個）**。

## Decision

選 3。流程：

```
獨立提案（平行、互相看不到）
  → 互評（評分表：正確性、簡潔度、風險、成本、可測試性）
  → 整合成「可直接交給工程師」的最終方案（含編號的驗收標準）
  → （選用）紅隊找漏洞 → 總結者修訂一次
  → ★ 核准關卡：你可以 核准（可先修改文字、填驗證指令）／要求修訂（最多 2 次）／只保留方案
  → 在 git worktree 實作（ADR 0004）
  → 驗證指令
  → 審查者依「驗收標準」逐條打勾（✅／❌／⚠️）
  → 有上限的修訂迴圈
```

決定性的兩個事實：

1. **第一輪要獨立**：兩個模型同時提案，看到的是同一份上下文（`Runner::parallel` 的 `visible`），避免第二個模型被第一個帶著走。
2. **核准關卡必須能撐過重啟**：等待核准可能要好幾個小時。狀態存成 `awaiting_approval`；重啟後 `recover_interrupted` 不會把它標成失敗，核准時由 `Engine::decide` 建立新的 runner，從實作階段接著做。

成本仍有上限：發言上限 = 2n + 1 + 紅隊 2 + 修訂 2 +（不只產出方案時）2r + 2，硬上限 24。

## Consequences

- 首頁預設模式改成「方案工作坊」。核准關卡預設要人決定；「自動核准」是選項，會跳出提醒。
- 驗收標準成為審查的依據，所以「審查通過」的意義比 v0.1 的協做模式更明確。
- 方案只產出不實作（`plan_only`），可以當成「需求→規格」的工具；模式比較實驗中，工作坊也一律以這種方式跑。
- 失去的：一路跑完的速度。換來的是：在最花錢的那一步之前，有一次人的判斷。
